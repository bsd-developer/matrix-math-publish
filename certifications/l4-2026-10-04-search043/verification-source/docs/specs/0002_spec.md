# 0002 — Conforming Series-Length Selection for Proved Logarithm Bounds

**Status:** Normative amendment to `0001_spec.md` §7.3  
**Document version:** 1.0.0  
**Date:** 2026-08-20  
**Audience:** an implementer with no prior repository context  
**Target:** the Lean checker under `lean/MatrixMath/`, cross-checked against the Rust and Python implementations of §7.3

---

## 0. Normative contract

This document specifies the remediation of one conformance defect found on 2026-08-20: the Lean checker does not select its logarithm series length the way `0001_spec.md` §7.3 requires. It defines the selection rule, fixes it in one place for all three implementations, states the Lean proof obligations, and fixes the acceptance evidence.

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative, with the meaning `0001_spec.md` §0 assigns them. Where this document conflicts with §7.3, this document governs; §0.1 records the amendment and its effect on document versions.

### 0.1 Relation to 0001

Everything in `0001_spec.md` that this document does not name explicitly is unchanged. In particular the trust model of §3, the directed-bound discipline of §7.1 and §7.2, the certificate schema of §6.5, and the Appendix A objective are untouched. This document changes what the second argument of the Lean directed logarithm API means, and with it how tight a bound Lean proves per evaluation. It changes no certificate field, no schema, and no published `Ω`. What the checker decides can change, however: a looser proved bound can in principle turn an acceptance into a rejection. §6 states the margin that makes that unlikely and the fallback if it happens anyway.

§7.3's sentence

> The implementation deterministically chooses the least series length whose proved tail enclosure is at most `2^-precision`; the certificate does not supply a trusted iteration count.

is amended in one respect only: the threshold becomes `2^-(precision+3)`, for the reason given in §3.1. The second clause is unchanged and is restated as a requirement in §3.5. Tightening the threshold only narrows the proved tail and therefore cannot make an accepted bound unsound.

The amended sentence carries no MUST, SHOULD, or MAY, and §2.3 of `0001_spec.md` reserves those keywords for requirements. The amendment therefore does not change a marked requirement, `0001_spec.md`'s document version stays `2.1.0`, and §0.5's rule that a document-version change updates the accepted `spec_version` atomically is not triggered. No committed certificate is re-emitted merely to carry a new version string. §7.3 MUST nevertheless gain a pointer to this document in the same change, so that the amended threshold is not discoverable only from a second file.

That reading is deliberate and it has a cost. §0.1 of `0001_spec.md` says the checked-in specification version and its source hashes identify the semantics of every certificate, and the amendment changes what the checker proves without moving either. The residual risk is carried in §9 and MUST NOT be closed by asserting that acceptance cannot change.

### 0.2 Prelaunch replacement policy

`0001_spec.md` §0.5 applies without qualification. The non-conforming Lean definitions are replaced, not deprecated. No implementation may retain a term-count-indexed entry point alongside a precision-indexed one, and no compatibility alias for the old argument meaning may exist. A dual path here would be worse than a migration cost: the two spellings have the same Lean type, so a caller could silently keep the old meaning.

## 1. The defect

### 1.1 What the specification requires

§7.3 defines the construction: write `x = m·2^e` exactly with `m ∈ [1,2)`, set `z=(m-1)/(m+1)`, evaluate `artanh(z)` as a series, and bound the discarded tail after `N` retained terms by

```text
z^(2N+1) / ((2N+1)(1-z^2)).
```

`precision` is a target number of binary fractional bits in `[32,4096]` (§6.5). It names an accuracy target, and the implementation derives `N` from it.

### 1.2 What Rust does

`crates/mm-rat/src/log2.rs::artanh_enclosure` takes a tolerance and accumulates terms until the proved tail is at most that tolerance:

```rust
let tail = next_power.checked_div(&tail_denominator)?;
if &tail <= tolerance {
```

`log2_enclosure` supplies that tolerance from the validated precision:

```rust
let tolerance = precision.tolerance()?;
let inner_tolerance = tolerance.checked_div(&Rat::from_integer(8))?;
```

`Precision::tolerance` returns `2^-precision`, so Rust selects the least `N` whose tail is at most `2^-(precision+3)`. The mechanism conforms: the length is derived, deterministic, and never read from a certificate. The threshold is three bits stricter than §7.3's literal text, which §3.1 makes normative rather than treating as drift. `python/mm_opt/log2.py` is a third independent implementation and makes the same two choices, with the comment `The same split the Rust implementation uses, so the two agree termwise.`

### 1.3 What Lean does

`lean/MatrixMath/Numeric/Log2Bounds.lean` indexes the directed API by a term count, not a precision:

```lean
def log2Lower (x : ℚ) (n : ℕ) : ℚ :=
  logLower (mantissa x) n / logTwoUpper n + (binExp x : ℚ)

def log2Upper (x : ℚ) (n : ℕ) : ℚ :=
  logUpper (mantissa x) n / logTwoLower n + (binExp x : ℚ)
```

`n` is the number of retained series terms: `logLower m n = logPartial (seriesVar m) n` and `logPartial z n = ∑ k ∈ range n, logTerm z k`. Nothing in the file computes a length from a tolerance.

`lean/MatrixMath/Certificate/OmegaCheck.lean` then passes the certificate's precision field into that slot. `TrackACert` declares

```lean
  /-- The §7.3 series precision used for every directed bound. -/
  precision : ℕ
```

and `check` threads `c.precision` into every directed bound, reaching `log2Lower (blk.y.getD a 0) prec` and `log2Upper ((I.q : ℚ) + 2) prec`. `lean/MatrixMath/Schema/Omega.lean` fills that field straight from the certificate:

```lean
  let (_, c) ← expectString ",\"payload\":{\"log_precision_bits\":" c
  let (precision, c) ← readNat limits c
```

A certificate declaring 256 bits therefore causes Lean to retain 256 terms of the mantissa series, and 257 of the `ln 2` series because `logTwoLower n = logLower 2 (n + 1)`.

The Lean call sites are not themselves wrong. Under the definition this document requires, `check` passing `c.precision` is exactly right, and `OmegaCheck.lean` needs no change. The defect lives entirely in what `Log2Bounds.lean` means by its second argument. Because the argument type is `ℕ` either way, a partial fix still compiles and still returns verdicts; the type checker reports nothing. That is why §4 requires value assertions.

### 1.4 Soundness status

Retaining more terms yields a tighter enclosure. The current Lean behaviour is therefore **sound but non-conformant**, and it makes Lean's bounds strictly tighter than the Rust and Python bounds on the same certificate. This is a live divergence between the authoritative checker and its independent cross-check, which is what §12.6's differential tests exist to surface.

Conforming will **loosen** Lean's bounds. §6 states the margin that makes that safe and what to do if a published certificate stops being accepted anyway. No result already published is retracted by this document: acceptance under a tighter enclosure remains a correct proof of the same statement.

## 2. Series-length arithmetic

### 2.1 The tail and its worst case

Write the §7.3 tail as

```text
seriesTail(z, n) = z^(2n+1) / ((2n+1)(1 - z^2)).                 (L1)
```

For `m ∈ [1,2)` the series variable `z=(m-1)/(m+1)` lies in `[0,1/3)`, and the `ln 2 = 2·artanh(1/3)` series uses `z = 1/3` exactly. So `z ≤ 1/3` on every call the checker makes, and `z = 1/3` is the worst case.

`seriesTail` is nondecreasing in `z` on `[0,1)` and nonincreasing in `n`, and strictly so for `0 < z`. The least `n` meeting a fixed threshold is therefore nondecreasing in `z` and nondecreasing in the threshold's bit count. Both facts are used below and are required as a metamorphic property in §8.

### 2.2 The least conforming length at 256 bits

At `z = 1/3` the factor `1 - z^2` is `8/9`, so

```text
seriesTail(1/3, N) = 3^-(2N+1) · 9 / (8(2N+1)).
```

Requiring `seriesTail(1/3, N) ≤ 2^-259`, which is §3.1's threshold at `precision = 256`, and taking base-two logarithms gives

```text
(2N+1)·log2 3 + log2(2N+1) ≥ 259 + 2·log2 3 - 3 = 259.16993.
```

With `log2 3 = 1.5849625`:

| `2N+1` | `N` | `(2N+1)·log2 3` | `log2(2N+1)` | sum | meets `259.16993` |
|---:|---:|---:|---:|---:|---|
| 157 | 78 | 248.83911 | 7.29462 | 256.13373 | no |
| 159 | 79 | 252.00904 | 7.31288 | 259.32192 | yes |

The least conforming length at `precision = 256` and `z = 1/3` is therefore **79**, and it is smaller for every mantissa with `z < 1/3`. Lean retains 256 terms, at least `256/79 = 3.24` times the required count, and proves a tail of about `2^-822` where `2^-259` is required.

Dropping the `1/((2N+1)(1-z^2))` factor and solving `(2N+1)·log2 3 ≥ 256` alone gives `2N+1 ≥ 163` and `N = 81`. That shortcut overstates the requirement, because the dropped factor is worth `log2(9/(8·159)) = -7.143` bits at this length, or `2.25` terms at `2·log2 3` bits per term. The factor MUST be retained. Appendix A is the normative table.

At `precision = 256` the literal §7.3 threshold `2^-256` happens to select 79 as well; `2N+1 = 157` misses it by `0.036` bits. The three-bit margin of §3.1 does change the selected length at other precisions: 10 rather than 9 at `precision = 32`, 160 rather than 159 at `precision = 512`, and 1290 rather than 1289 at `precision = 4096`.

### 2.3 The selection cap

Because the least conforming length is nondecreasing in both `z` and `precision` (§2.1), the largest length the supported range can demand occurs at `z = 1/3` and `precision = 4096`. Applying §2.2's inequality with the threshold `2^-4099`:

| `2N+1` | `N` | `(2N+1)·log2 3` | `log2(2N+1)` | sum | meets `4099.16993` |
|---:|---:|---:|---:|---:|---|
| 2579 | 1289 | 4087.61829 | 11.33260 | 4098.95089 | no |
| 2581 | 1290 | 4090.78821 | 11.33371 | 4102.12193 | yes |

`1290` is the maximum. §3.2 fixes the search cap at `8192`, which is `6.35` times that maximum. The cap exists to make the function total by structural recursion, not to bound normal operation.

### 2.4 Cost of the excess terms

The `k`-th retained term is `z^(2k+1)/(2k+1)`. For `z = a/b` in lowest terms, `z^(2k+1)` carries a numerator of about `(2k+1)·log2 a` bits over a denominator of about `(2k+1)·log2 b` bits, so operand size grows linearly in the term index and so does the accumulator's denominator. Total exact-rational work over `n` terms therefore grows at least quadratically in `n`, not linearly.

Under that quadratic model, retaining 256 terms where 79 suffice costs about `(256/79)^2 = 10.5` times the series arithmetic. This is an estimate whose assumption is the quadratic cost model; the end-to-end effect on Lean wall clock is **not yet measured**, and §7 requires it to be measured against the recorded baseline rather than asserted.

## 3. Normative selection rule

### 3.1 The selection threshold

The threshold is

```text
seriesTarget(precision) = 2^-(precision+3).                      (L2)
```

Every implementation MUST select against L2 and MUST NOT select against `2^-precision`.

The three-bit margin is the tolerance split already present in `crates/mm-rat/src/log2.rs::log2_enclosure` and `python/mm_opt/log2.py::log2_enclosure`. One `log2` evaluation composes two series enclosures, two doublings, a reciprocal, and a product, and the margin absorbs that composition. Making it normative is a clean replacement for two implementations that already behave this way, and it leaves the Rust and Python verdicts on every existing artifact unchanged. The alternative — loosening Rust and Python to the literal `2^-precision` — would change three implementations instead of one and would widen the enclosures that produced the published results.

The composed enclosure width is **not** claimed to be at most `2^-precision`. That remains an open question, and nothing in the checker depends on it: §7.2's inequality needs direction, not width, and a wider enclosure yields a worse bound rather than an unsound one.

### 3.2 The series-length function

Each of Lean, Rust, and Python MUST expose selection as a named total function of `(z, precision)`:

```text
seriesLength(z, precision) = the least n ≤ 8192 with
                             seriesTail(z, n) ≤ seriesTarget(precision),
                             or 8192 when no such n exists.               (L3)
```

The Lean definition MUST be total and executable, and MUST terminate structurally on a fuel argument bounded by the cap. It MUST NOT be stated in a form whose totality depends on `precision` lying in `[32,4096]`; the range check belongs to the decoder (§6.5), and a numeric helper that diverges on out-of-range input is a rejection path waiting to be reached by a future caller.

Reaching the cap MUST be treated as a failure rather than a result. Rust MUST return the stable `resource_limit` code instead of a length that does not meet L2. Python is the producer and carries no exit code, so it MUST raise instead of returning such a length. Lean's total function returns the cap instead. That needs no separate unreachability theorem: L4 (§5) is stated over the whole supported domain, so proving it establishes that the returned value satisfies L2 there whether or not it is the cap.

The cap is `8192`. The previous Rust and Python guard of `100_000` is replaced, not kept alongside it.

An implementation MAY fuse length selection into the loop that accumulates the partial sum, so that terms are not computed twice. If it does, a test MUST assert that the fused loop's final term count equals `seriesLength(z, precision)` on the §4.1 vectors. The fused count is an optimization; L3 is the definition.

A fused loop MUST test the tail before accumulating the first term, so that it can return zero. The current `crates/mm-rat/src/log2.rs::artanh_enclosure` and `python/mm_opt/log2.py::artanh_enclosure` accumulate one term before their first test and special-case `z = 0` ahead of the loop, so they return `1` for every nonzero `z`. L3 returns `0` for every `z` with `z/(1-z^2) ≤ seriesTarget(precision)`, which a mantissa just above `1` reaches without being exactly `1`. Left unfixed, that is a new Lean/Rust divergence introduced by this change rather than removed by it, so §4.1 requires a vector for it.

### 3.3 Required properties

Every implementation of L3 MUST satisfy:

1. `seriesTail(z, seriesLength(z, precision)) ≤ seriesTarget(precision)` for `0 ≤ z ≤ 1/3` and `32 ≤ precision ≤ 4096`; and
2. `1 ≤ seriesLength(1/3, precision)` for `32 ≤ precision`.

Property 1 is the whole point of the rule and is stated as L4 in §5. Property 2 is what keeps the `ln 2` lower endpoint strictly positive so it can be used as a divisor (§7.2); `seriesTail(1/3, 0) = 3/8`, which exceeds `2^-35`, so it holds with wide room and MUST be proved rather than assumed.

### 3.4 The directed API

The Lean directed API MUST be indexed by precision:

```text
logLower(m, precision)  = logPartial(seriesVar(m), seriesLength(seriesVar(m), precision))
logUpper(m, precision)  = logLower(m, precision)
                          + logTailBound(seriesVar(m), seriesLength(seriesVar(m), precision))
logTwoLower(precision)  = logLower(2, precision)
logTwoUpper(precision)  = logUpper(2, precision)
log2Lower(x, precision) = logLower(mantissa(x), precision) / logTwoUpper(precision) + binExp(x)
log2Upper(x, precision) = logUpper(mantissa(x), precision) / logTwoLower(precision) + binExp(x)
```

`seriesVar(2) = 1/3`, so the `ln 2` series is the `m = 2` case of the same rule and needs no separate length. The current `logTwoLower n = logLower 2 (n + 1)` shift MUST be deleted; it exists only to make the positivity lemma applicable, and §3.3's property 2 replaces it.

The two lengths inside one `log2` evaluation differ in general — one for the mantissa's `z`, one for `1/3` — exactly as they already do in Rust. An implementation MUST NOT reuse the `ln 2` length for the mantissa series or the reverse.

`Log2Bounds.lean` retains its existing tail bound `logTailBound z n = 2·z^(2n+1)/((2n+1)(1-z^2))`, which bounds the doubled series `log(1+z) - log(1-z)` that the file actually sums. The relation to L1 is exactly

```text
logTailBound(z, n) = 2 · seriesTail(z, n),
```

so the L3 predicate expressed on `logTailBound` is `logTailBound(z, n) ≤ 2^-(precision+2)`. Implementers MUST select on L1 as written and MUST NOT transcribe L2's exponent onto the doubled bound; the factor of two is the most likely transcription slip in this change, and the §4.1 vectors are the check that catches it.

### 3.5 `log_precision_bits` remains a target

`log_precision_bits` is a target accuracy, never a trusted iteration count. This restates §7.3 and §6.5 and is unchanged by this document.

Concretely, the checker MUST derive every series length from the certificate's precision field through L3, and MUST NOT use that field, or any other certificate field, as a term count, loop bound, or array length. The schema decoder MUST continue to reject `log_precision_bits` outside `[32,4096]` before evaluation, with the stable code the `schemas/fixtures/invalid/omega_bad_precision.json` fixture pins.

A certificate MUST NOT gain a field carrying a series length, a term count, or a tail bound. Such a field would move an iteration count into the trusted path, which is the failure mode §7.3's second clause forbids.

## 4. Cross-implementation agreement

### 4.1 The shared vectors

Lean, Rust, and Python MUST select the same length for the same `(z, precision)`. Since all three compute the least `n` satisfying one rational predicate, agreement is a consequence of the definition; the test exists to catch a transcription error in one of them, which is the reason §4.1 of `0001_spec.md` requires three independent implementations at all.

A committed vector file `tests/vectors/series-length.json` MUST carry `(z, precision, terms)` triples in the §6.2 rational grammar, covering at minimum: `z = 0`; the exact worst case `z = 1/3`; at least three mantissa-derived values strictly between; one nonzero `z` small enough that zero terms meet L2, which is the §3.2 fused-loop trap; and the endpoints `precision = 32` and `precision = 4096` as well as the `256` that every current experiment configuration uses. Appendix A is the normative table those triples MUST reproduce.

The vector file MUST be committed data, not regenerated by any of the three implementations. A generated table would only prove that the generator agrees with itself.

### 4.2 The differential check

`scripts/differential-check.py` MUST gain a series-length stage that reads `tests/vectors/series-length.json`, obtains each implementation's value, and compares all three. Any Lean/Rust disagreement MUST return exit code 6 and block release, as §12.6 requires of every exact disagreement. Python disagreement MUST fail the run as well: the producer computes each block's `ε` against its own §7.3 implementation, so a Python length that differs from the checker's yields an `ε` that does not dominate what the checker proves, and the certificate is rejected after the expensive part.

The Lean value MUST come from the compiled Lean definition — a script under `lean/scripts/` in the manner of `lean/scripts/DecodeCheck.lean`, invoked by `just test-diff` — and MUST NOT be transcribed into the Python harness. The Rust value MUST come from `crates/mm-rat`. Reading a constant out of the vector file and comparing it against itself is not a differential test.

`crates/mm-rat/tests/numerics.rs` MUST additionally assert the Appendix A values directly, so the Rust side fails at `just test` and not only at `just test-diff`.

## 5. Lean proof obligations

The following MUST hold after the change.

1. The specialization theorem

   ```text
   seriesTail(z, seriesLength(z, precision)) ≤ seriesTarget(precision)     (L4)
   ```

   for `0 ≤ z ≤ 1/3` and `32 ≤ precision ≤ 4096`, named `seriesLength_tail_le`. L4 is what makes the selected length meaningful; without it `seriesLength` is an arbitrary total function.

2. `1 ≤ seriesLength(1/3, precision)` for `32 ≤ precision`, and hence `0 < logTwoLower(precision)`, replacing the current `logTwoLower_pos` proof that relies on the `n + 1` shift.

3. `log2Lower_le` and `le_log2Upper` continue to hold with the selected length, restated at `precision`:

   ```text
   log2Lower x precision ≤ logb 2 x        for 0 < x
   logb 2 x ≤ log2Upper x precision        for 0 < x
   ```

   These are the two theorems the checker's soundness proof consumes, and their statements change even though their content does not. §8 requires the corresponding assurance-manifest update.

4. `TrackACert.check_sound` and `Schema.omega_le_of_acceptsOmega` MUST continue to hold with no new hypothesis and no new axiom. The permitted project axiom remains exactly `AX1_combination_loss` (§3.2 of `0001_spec.md`).

The general tail lemma `le_logPartial_add_tail`, currently proved for an arbitrary `n`, MUST be retained. Restating it only at the chosen length would delete a proved general fact that both the mantissa specialization and the `ln 2` specialization consume as input, and L4 is derived from it rather than in place of it. The requirement that a term count never escapes is stated instead as a prohibition: no exported directed function and no soundness theorem may be indexed by a raw term count. The arbitrary-`n` lemma is a private helper feeding L4.

`logPartial_le` and `le_logPartial_add_tail` keep their statements and therefore their recorded statement digests.

## 6. Safety margin

### 6.1 Measured slack

Conforming loosens Lean's proved tail from about `2^-822` to `2^-259` per evaluation (§2.2). The first two rows below are measured and recorded in `docs/experiments/omega-l3.md`; the third is L2 evaluated at the precision every current experiment configuration uses, and is what the first two are being compared against:

| Quantity | Value | As a power of two |
|---|---:|---:|
| largest block `ε` | `7.5 × 10^-10` | `2^-30.3` |
| certification gap | `3.5 × 10^-12` | `2^-38.1` |
| series tolerance at `precision = 256` | `1.1 × 10^-78` | `2^-259` |

The `ℓ*=3` certificate has 5,779 nodes and 762 maximum-entropy blocks. The number of logarithm evaluations it costs is recorded nowhere and no implementation counts it, so the `10^6` below is an assumed over-estimate rather than a measurement. At that count the aggregate series contribution is at most `10^6 × 1.1 × 10^-78 = 1.1 × 10^-72` in the units the objective is measured in, about 63 orders of magnitude below the largest block `ε`. Dividing by the measured `lower(M_total) = 3.015265574536` converts it to at most `3.7 × 10^-73` in `Ω`, about 61 orders of magnitude below the `3.5 × 10^-12` certification gap. The conclusion does not depend on the assumed count: sixty orders of magnitude of headroom survive any correction the true count could supply.

The `ε` and gap figures are dominated by the 48-bit rational rounding of the free variables, not by the logarithm bounds, which is the same finding `docs/experiments/omega-l3.md` already records for the 256-bit bounds.

### 6.2 If a published certificate stops being accepted

The acceptance margin of the published `ℓ*=3` certificate is the amount by which `eTotalLower + mTotalLower·Ω` exceeds `requirementUpper`, which is the inequality `TrackACert.check` decides. It is **not separately recorded**. The `3.5 × 10^-12` figure is the float-versus-certified gap, which bounds that margin from above but does not measure it.

Nor do the recorded quantities settle it. `docs/experiments/omega-l3.md` records `Ω` exactly but states `lower(E_total)`, `lower(M_total)`, and the requirement only to twelve decimal places. Propagating those roundings through `eTotalLower + mTotalLower·Ω - requirementUpper` leaves `±2 × 10^-12`, which does not fix even the sign of a margin the same source bounds above by `3.5 × 10^-12`. §6.1's arithmetic therefore shows the change is negligible relative to the recorded slack, not that acceptance is arithmetically guaranteed. M4-R MUST record the exact margin when it runs `just verify`, so the next change to the numerics has a measurement to reason from.

If a published certificate stops being accepted after the change, the producer MUST re-emit it at a larger `Ω` from the recorded run and republish under a new canonical digest. The checker MUST NOT be loosened back, the threshold MUST NOT be moved, and a term count MUST NOT be reintroduced to recover the old bound. A bound that survives only under a non-conforming checker was never the bound that was claimed.

Certificate bytes are unchanged by this work. `Ω` is carried by the certificate and the checker only decides it, so an accepted certificate reports the identical bound before and after. No file under `tests/vectors/`, `data/`, or `lean/MatrixMath/Generated/` is regenerated: the generated modules carry published bytes and invoke `acceptsOmega`, and neither changes.

## 7. Remediation milestone

### 7.1 M4-R — conforming series-length selection

M4-R is a remediation of M4 (§14.7) and M5 (§14.8), both of which are recorded complete. It is not a new position in the M-1 through M8 sequence. It SHOULD land before any `ℓ*=4` Lean throughput figure is extrapolated from the `ℓ*=3` measurement, because that measurement is taken under the non-conforming length and §2.4's cost model is unmeasured. This document does not otherwise gate M7.

**Inputs:** M4 and M5, both complete.  
**Deliverables:** `seriesLength` in Lean, Rust, and Python; a precision-indexed Lean directed API with L4; committed shared vectors; a differential stage comparing all three; and updated traceability, assurance manifest, errata, experiment record, and implementation status.

Implementation order:

1. add `seriesTail`, `seriesTarget`, and `seriesLength` to `lean/MatrixMath/Numeric/Log2Bounds.lean` as a fuel-bounded total function with cap 8192;
2. prove L4 and `1 ≤ seriesLength(1/3, precision)`;
3. reindex `logLower`, `logUpper`, `logTwoLower`, `logTwoUpper`, `log2Lower`, and `log2Upper` by precision, deleting the `n + 1` shift and every term-count entry point;
4. restate and re-prove `log2Lower_le` and `le_log2Upper`, then rebuild `TrackACert.check_sound` and `Schema.omega_le_of_acceptsOmega` unchanged in content;
5. expose `series_length` in `crates/mm-rat/src/log2.rs` and in `python/mm_opt/log2.py`, move the tail test ahead of the first accumulation so a zero length is reachable, and replace the `100_000` guard with the cap and the `resource_limit` rejection;
6. commit `tests/vectors/series-length.json` from Appendix A and assert it in `crates/mm-rat/tests/numerics.rs`;
7. add the Lean series-length script and the `scripts/differential-check.py` stage; and
8. update `docs/traceability.toml`, the assurance manifest, `docs/errata.md`, `docs/experiments/omega-l3.md` with the measured acceptance margin and Lean wall clock, and `docs/implementation-status.md`.

Acceptance commands:

- `seriesLength(1/3, 256)` evaluates to 79 in all three implementations, `seriesLength(1/3, 4096)` to 1290, and `seriesLength(2^-64, 32)` to 0;

## 9. Risks and fixed fallbacks

| Risk | Detection point | Required fallback |
|---|---|---|
| A published certificate stops being accepted under the conforming length | M4-R acceptance run of `just verify` and `just prove` | re-emit at a larger `Ω` from the recorded run and republish under a new digest; never restore the non-conforming length |
| Lean and Rust select different lengths | `just test-diff` | exit 6, quarantine the artifact, diagnose before release |
| Python selects a different length from the checker | `just test-diff` | fail the run and correct the producer; a mismatched `ε` fails after the expensive part, not before it |
| `seriesLength` reaches the cap inside the supported range | any evaluation | return `resource_limit`; never fall back to a fixed length or a widened threshold |
| The doubled tail bound is used with L2's exponent | Appendix A vectors | fail the build; the factor of two is the expected transcription slip and the vectors are its only cheap detector |
| A partial fix leaves the second argument meaning a term count | Appendix A value assertions in `just test` | fail the build; the argument type is unchanged, so nothing else catches it |
| A fused loop retains one term where L3 selects zero | the `z = 2^-64` Appendix A vectors | fix the loop to test the tail before the first accumulation; never special-case the vector |
| The conforming checker's acceptance set differs from the non-conforming one, with no `spec_version` change to mark it | M4-R acceptance run of `just verify` and `just prove` | record the difference in `docs/errata.md` and escalate §0.1's amendment to a `0001_spec.md` document-version increment under §0.5; never leave a changed acceptance set unrecorded |
| The Lean wall clock does not improve | M4-R measurement against 110 minutes | record the measurement as a negative result and keep the conforming length |

No fallback may reintroduce a certificate-supplied iteration count, and no fallback may widen L2 without a further amendment.

## Appendix A — Reference series lengths

Normative values of `seriesLength(z, precision)` under L2 and L3. `m` is the mantissa the `z` column derives from through `z = (m-1)/(m+1)`; the `ln 2` series is the `m = 2` row.

| `m` | `z` | `precision` | `seriesLength` |
|---|---|---:|---:|
| 1 | `0` | 256 | 0 |
| `(2^64+1)/(2^64-1)` | `2^-64` | 32 | 0 |
| `(2^64+1)/(2^64-1)` | `2^-64` | 256 | 2 |
| `(2^64+1)/(2^64-1)` | `2^-64` | 4096 | 32 |
| `5/4` | `1/9` | 256 | 40 |
| `45/32` | `13/77` | 256 | 49 |
| `3/2` | `1/5` | 256 | 54 |
| `7/4` | `3/11` | 256 | 67 |
| 2 | `1/3` | 32 | 10 |
| 2 | `1/3` | 256 | 79 |
| 2 | `1/3` | 4096 | 1290 |

The `z = 0` row is the exact-power-of-two case: `seriesTail(0, 0) = 0`, so the least conforming length is zero and the partial sum is the exact value `0`. Rust short-circuits this case before the series and Python does the same; Lean reaches it through the general definition and gets the same answer, which is why the row is a vector rather than a special case in the specification.

The `z = 2^-64` rows are the §3.2 fused-loop trap. The mantissa is not `1`, so neither short-circuit fires, yet at `precision = 32` the tail already meets L2 before any term is retained. A loop that accumulates before it tests returns `1` here and disagrees with Lean. The same `z` at `precision = 256` and `precision = 4096` returns `2` and `32`, so the three rows also exercise monotonicity in `precision` on one fixed `z`.

`tests/vectors/series-length.json` MUST reproduce this table exactly. A change to any value is a change to L2 or L3 and requires an amendment to this document.
