# 0004 — Precision selection for directed bounds

**Status:** Normative producer policy amending `0001_spec.md` §7.3 and §14.9  
**Document version:** 1.0.0  
**Date:** 2026-08-20  
**Audience:** an implementer with no prior repository context  
**Target:** the Track A certificate producer in `python/mm_opt/` and the run configurations under `experiments/`

---

## 0. Normative contract

This document fixes how the Track A producer chooses a certificate's `log_precision_bits`, and lowers the value the repository ships. Every Track A certificate this repository has produced declares 256. No file in the repository derives that number, and the measurements recorded in `docs/experiments/omega-l3.md` show that roughly two hundred of those bits do nothing.

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative, with the meaning `0001_spec.md` §0 assigns them. This document is a versioned amendment in the sense of that section: where it conflicts with §7.3 or §14.9, this document governs.

What follows is a producer policy plus a default. The certificate schema, the accepted range, and the meaning of every existing field are unchanged, and §6 of this document states that as a prohibition rather than leaving it to be inferred.

### 0.1 Relation to 0001 and 0002

`0001_spec.md` §6.5 makes `log_precision_bits` a certificate field in the inclusive range 32–4,096. §7.3 makes it a target number of binary fractional bits and forbids treating it as a trusted iteration count. Neither section says how a producer picks a value inside the range; this document supplies that rule.

`0002_spec.md` fixes how each implementation turns a precision into a series length, and amends §7.3's threshold to `2^-(precision+3)` per series. That work is upstream of this one: 0002 decides what one evaluation guarantees, and this document decides how many bits to ask for. The two are independent — 0002's rule is correct at any precision in the range, and this document's rule is correct under any conforming series-length selection.

Nothing here changes what the checker decides. §4.5 restates the checker's obligations so that an implementer reading only this document does not weaken them.

### 0.2 Prelaunch replacement policy

`0001_spec.md` §0.5 applies without qualification. The 256-bit default is replaced, not deprecated. No configuration file, producer entry point, or `just` recipe may retain the old default alongside the new one, and no flag may exist whose only purpose is restoring it. An explicit `--precision` override remains, because §4.4 requires it to be recorded as an override and because a research run that deliberately asks for more bits is a legitimate experiment rather than a compatibility shim.

Certificates already produced are not regenerated. §5.3 says which artifacts are rebuilt and which are left exactly as they stand.

## 1. The value in use

### 1.1 What the field carries

`log_precision_bits` is a target accuracy for the §7.3 directed logarithm bounds. It is declared data: the schema decoder validates it against `[32,4096]` (§6.5) and the evaluator derives a series length from it (§7.3, `0002_spec.md` §3.2). It is not a term count, a loop bound, or an array length, and the checker never trusts it as one.

Raising it narrows every directed enclosure, which can only make the checker's verdict more conservative. Lowering it widens every enclosure, which can only make the verdict less generous. Neither direction can make an accepted bound unsound. This asymmetry is the whole reason a producer policy is enough here and a checker change is not needed.

### 1.2 What chose 256

Nothing did. The value appears as a literal in every place a Track A run configures itself:

| Location | Value |
|---|---:|
| `experiments/omega-l2/config.toml` | 256 |
| `experiments/omega-l2/smoke.toml` | 256 |
| `experiments/omega-l3/config.toml` | 256 |
| `experiments/omega-l3/refine.toml` | 256 |
| `experiments/lstar4/config.toml` | 256 |
| `python/mm_opt/optimize.py` fallback | 256 |
| `python/mm_opt/certify.py` fallback | 256 |
| `python/mm_opt/omega_fixtures.py` default argument | 256 |
| `justfile` recipe `certify RUN PRECISION` | `"256"` |

No comment, ADR, or experiment record derives it, and `crates/mm-exact/tests/omega_fixtures.rs` asserts the literal 256 on the hand fixture. A number repeated in nine places and justified in none is a default by inertia.

### 1.3 What actually binds the certified value

`docs/experiments/omega-l3.md` records the `ℓ*=3` result and the three quantities that matter here. Read out of `tests/vectors/omega-l3-optimized.json`, the largest §7.4 block slack is exactly

```text
max ε = 210049 / 2^48 = 7.4624 × 10^-10 = 2^-30.32,
```

which the experiment record rounds to `7.5 × 10⁻¹⁰`. The recorded float-versus-certified gap is `3.5 × 10⁻¹²`, or `2^-38.06`. The per-evaluation series tolerance at 256 bits is `2^-256`, about `8.6 × 10^-78`.

The gap between `2^-30.32` and `2^-256` is 226 binary orders. The experiment record already states the conclusion in words — the slack is dominated by the 48-bit rational rounding of the free variables, not by the logarithm bounds — and §3 of this document states it as arithmetic. The precision is not the binding constraint on the certified value. The rational rounding is.

The same picture holds one level down. At `ℓ*=2` the certificate rounds free variables at 40 bits, `tests/vectors/omega-l2-optimized.json` carries a largest `ε` of `5.4570 × 10^-11` (`2^-34.09`), and `docs/experiments/omega-l2.md` records a gap of `8.5 × 10⁻¹¹`. Both instances sit more than 220 binary orders above their series tolerance.

Two instances are not enough to establish how `ε` depends on `rational_bits`: the `ℓ*=3` point rounds at *more* bits than the `ℓ*=2` point and still emits a *larger* `ε`, because the domains and the tree differ. That relation is an open question, and §4.3 requires the rule to use the `ε` the producer measures rather than a formula in `rational_bits`.

## 2. Error model

### 2.1 One evaluation

One directed logarithm evaluation returns an enclosure of `log2 x`. The producer's derivation MUST treat its width as at most

```text
tol(precision) = 2^-precision.                                   (P1)
```

`0002_spec.md` §3.1 makes each of the two series inside one evaluation meet `2^-(precision+3)`, and the surrounding composition — a doubling, a reciprocal of the `ln 2` enclosure, and a product — is what the three spare bits pay for. `crates/mm-rat/tests/numerics.rs` asserts `enclosure.width() <= 2^-bits` for `bits` of 32, 64, 128, and 256 on a committed table of values, so P1 holds wherever it has been checked. `0002_spec.md` §3.1 records the general statement as an open question. The margin in §4.2 is three decimal orders wide, which absorbs a constant-factor error in P1 many times over.

### 2.2 How many evaluations one check performs

Every directed logarithm evaluation in a Track A check originates at one of eight places in `lean/MatrixMath/Certificate/OmegaCheck.lean`:

| Source | Definition | Evaluations |
|---|---|---|
| §7.4 block closeness | `blockOk` | `log2Lower` and `log2Upper` of each `y(a)`, per block |
| §7.4 witness entropy | `penaltyUpper` via `hUpper` | one per positive entry of `y`, per block |
| §7.4 domain entropy | `penaltyUpper` via `hLower` | one per positive entry of `ρ`, per block |
| root marginal entropies | `eRootRegionLower` | one per positive entry of each of three distributions, per region |
| interior marginal entropies | `eInteriorRegionLower` | the same, per positive interior node per region |
| conditional mixtures | `etaYUpper`, `etaZUpper` | one per positive entry of each child and mixture list |
| level-2 exponent | `eTwoSumLower` | one per positive entry of `levelTwoList`, per node, per coordinate |
| local sizes and the requirement | `mTotalSumLower`, `requirementUpper` | one `log2Lower(q)` per leaf per coordinate, plus one `log2Upper(q+2)` |

The count is a function of the instance shape and of which entries are zero. It does not depend on the precision, which is why a producer can obtain it before deciding the precision.

It was measured by incrementing a counter inside `log2_enclosure` in `crates/mm-rat/src/log2.rs` and running `mm verify --skip-lean`. The Rust evaluator computes both endpoints of the §7.4 closeness test from one enclosure where the Lean checker calls `log2Lower` and `log2Upper` separately, so the Lean checker performs one extra evaluation per block domain point. Charging that difference gives a count valid for both:

```text
K = evaluator evaluations + block domain points.                 (P2)
```

For `tests/vectors/omega-l3-optimized.json` — 762 blocks over 5,778 domain points, the tree of 5,779 nodes recorded in `docs/experiments/omega-l3.md` — the evaluator performs 77,234 evaluations, so

```text
K(ℓ*=3) = 77,234 + 5,778 = 83,012.                               (P3)
```

`tests/vectors/omega-l3-uniform.json` has the same tree, the same 762 blocks, and the same 5,778 domain points, and produces the identical evaluator count. For `tests/vectors/omega-l2-optimized.json` — six blocks over 90 domain points — the evaluator performs 938, so `K(ℓ*=2) = 1,028`.

The instrumentation used to obtain those figures is not committed. §4.1 makes the count a reported field instead, so that a producer never has to patch the evaluator to apply the rule.

### 2.3 Accumulation

The producer's derivation MUST assume that every evaluation contributes its full width, with weight one, in the direction that worsens the checker's verdict:

```text
seriesError(K, precision) = K · 2^-precision.                    (P4)
```

The objective is measured in bits, and so is `ε`, so P4 and `ε` are directly comparable. To compare P4 against a bound on `ω`, divide by the certificate's `lower(M_total)`, which is what turns a shift in `E_total` into a shift in the least `Ω` that satisfies A21.

### 2.4 Why P4 is an over-estimate

Most evaluations enter through an entropy of a probability distribution. In `hLower(l, prec) = Σ -p·log2Upper(p, prec)`, the error of each term against the true `-p·log2 p` is `p` times the enclosure width, and the entries sum to one, so the whole entropy of a distribution is displaced by at most one `tol(precision)` no matter how long the list is. Counting each entry separately therefore over-charges every entropy by its length.

P4 is nonetheless the rule's model, for two reasons. The weights outside entropies — node masses, the region weights `A_T^(r)`, and the `η` mixture weights of A8 and A12 — are validated nonnegative by §7.2 but are not all bounded by one, so a weight-aware bound is not available without further proof. And the over-charge is cheap: it costs `log2 K` bits of precision, which at `ℓ*=3` is 16.34 bits out of 57.

## 3. The arithmetic at `ℓ*=3`

Throughout this section `K = 83,012` from P3, `ε = 7.4624 × 10^-10` from §1.3, the certification gap is `3.5 × 10⁻¹²`, and `lower(M_total) = 3.015265574536` as recorded in `docs/experiments/omega-l3.md`.

### 3.1 Sixty-four bits

`2^-64 = 5.4210 × 10^-20`. By P4,

```text
seriesError = 83,012 × 5.4210 × 10^-20 = 4.5001 × 10^-15 bits,
            = 4.5001 × 10^-15 / 3.015265574536
            = 1.4924 × 10^-15 in Ω.
```

Against the two measured quantities:

| Comparison | Ratio |
|---|---:|
| largest block `ε` over the accumulated series error | `1.66 × 10^5` |
| certification gap over the accumulated error in `Ω` | `2.35 × 10^3` |

Sixty-four bits leaves the block slack five decimal orders clear and the recorded gap three decimal orders clear. Both margins are against measurements the producer already records, not against estimates.

### 3.2 Thirty-two bits

`2^-32 = 2.3283 × 10^-10`, which is the same order as `ε` itself: one evaluation at 32 bits is `0.31 ε`, and `ε` is only `3.22` times it. Accumulated over the whole check,

```text
seriesError = 83,012 × 2.3283 × 10^-10 = 1.9328 × 10^-5 bits,
            = 6.4100 × 10^-6 in Ω.
```

That is `2.59 × 10^4` times **larger** than the block slack it must not disturb, and `1.83 × 10^6` times larger than the recorded certification gap. Thirty-two bits is not acceptable at this instance, and the schema minimum is therefore not a usable default. The single-evaluation comparison is the sharper statement: a rule that let one evaluation reach a third of `ε` would be indefensible even if the accumulation model were far more generous than P4.

### 3.3 Two hundred fifty-six bits

`2^-256 = 8.6362 × 10^-78`, so `seriesError = 7.1691 × 10^-73` bits, which is `1.04 × 10^63` times below `ε`. Sixty-three decimal orders of unused margin is the measurement that motivates this document. `0002_spec.md` §6.1 reaches the same conclusion from a deliberately crude over-estimate of `10^6` evaluations; P3 replaces that over-estimate with a count.

### 3.4 The direction of the failure

Choosing too few bits does not produce a false theorem. Every directed bound stays valid at every precision in the range; a precision that is too low widens the enclosures, which lowers `lower(E_total)`, raises `upper(log2(q+2))`, and makes the A21 inequality harder to satisfy. The checker rejects, or the producer's two-pass search for the least accepted `Ω` returns a worse value.

What it destroys is time. At `ℓ*=3` the Lean `native_decide` proof takes 110 minutes uncontended (`docs/experiments/omega-l3.md`), and it runs after the optimizer, the exact producer, and the Rust evaluation. Discovering a bad precision at that point costs the whole pipeline. That is why P4 is deliberately pessimistic and why §4.2 imposes a margin rather than requiring only that the accumulated error be smaller than `ε`.

## 4. The selection rule

### 4.1 The evaluation-count bound

`mm omega-min` MUST report the P2 count as a field named `log_evaluations` in its JSON object, counting each endpoint of the §7.4 closeness test separately so that the reported figure bounds the Lean checker as well as the Rust evaluator. The producer already runs `mm omega-min` on a placeholder certificate as the first of the two passes described in `python/mm_opt/certify.py`, so the count costs nothing extra.

The producer MUST take `K` from that field and MUST NOT substitute a constant, an estimate from the node count, or a figure carried over from another instance. A hard-coded `K` would silently stop tracking the instance the moment `ℓ*` or the tree shape changed, which is exactly the failure this document exists to end.

`K` MUST NOT appear in a certificate. It is a producer input, and a certificate field carrying an evaluation count would move a loop bound into the trusted path (§7.3, `0002_spec.md` §3.5).

### 4.2 The margin condition

Let `ε_emit` be the largest §7.4 block slack the producer will write into the certificate. The producer MUST choose

```text
precision = least p ∈ [32,4096] with K · 2^-p ≤ ε_emit / 1000.   (P5)
```

The fixed fraction is one thousandth. It costs `log2 1000 = 9.97` bits: at `ℓ*=3` the bare condition `K · 2^-p ≤ ε_emit` is met at `p = 47` and P5 at `p = 57`. Ten bits is the cheapest insurance in the pipeline against the composition constant in P1, against the weights P4 ignores, and against an instance whose `K` grows faster than its `ε`.

`ε_emit` is itself computed from directed logarithm enclosures at the declared precision (`python/mm_opt/certify.py`), so P5 refers to the value it selects. `ε(p)` is non-increasing in `p`, so the producer MUST evaluate P5 at the precision it actually emits, by iterating: compute `ε` at the current precision, apply P5, and repeat if P5 selects a larger precision. Each iteration raises the precision, so the loop terminates. The producer MUST stop after four iterations and return the existing `rationalization_failed` code rather than emitting a certificate whose recorded derivation does not hold at its own precision.

In practice the loop settles immediately, because `ε` is rounded up to a `rational_bits`-bit dyadic before it is emitted: the `ℓ*=3` certificate's largest `ε` is exactly `210049/2^48`, and a change of enclosure width from `2^-256` to `2^-64` cannot move a multiple of `2^-48` unless a residual lies within `2^-64` of a rounding boundary.

That same rounding gives a floor. A nonzero emitted `ε` is a positive multiple of `2^-rational_bits`, so

```text
p ≥ rational_bits + ceil(log2 K) + 10                            (P6)
```

satisfies P5 for every nonzero `ε_emit` without measuring one. A producer that cannot yet compute `ε` MAY use P6. It is strictly weaker: at `ℓ*=3` it selects 75 where the measured `ε` selects 57, because the measured `ε` of `2^-30.32` sits far above the `2^-48` floor.

### 4.3 Precision and `rational_bits` are chosen together

The certified value is limited by whichever of the two is looser, and at both recorded instances that is the rational rounding by more than two hundred binary orders. The producer MUST therefore choose `rational_bits` first, from the `Ω` the run is trying to certify, and `precision` second, from the resulting `ε` through P5.

The producer MUST NOT raise `precision` in response to an `ε` that is too large. Precision cannot repair rational rounding: `ε` is a ceiling on the residual `|log2 y(a) - g(a)|` of a point whose free variables have already been rounded, and tightening the enclosure of `log2 y(a)` moves that residual by at most one `tol(precision)`. The remedy for a large `ε` is more `rational_bits`, at the cost `docs/experiments/omega-l3.md` records — a uniform `ℓ*=3` certificate proves in 37 minutes and the 48-bit optimized one in 110, because every entropy term carries three times the digits.

A run configuration MUST set both `log_precision_bits` and `rational_bits` in its `[run]` table. Neither may be left to a producer fallback, because a fallback is how the pair silently stops being a pair.

### 4.4 The certification record

`python/mm_opt/certify.py` already writes a `matrix-math-certification-record/1` object to `<run>/certification.json` carrying `log_precision_bits`, `rational_bits`, `max_epsilon`, `gap`, and the certified and float values of `Ω`. That schema is replaced by `matrix-math-certification-record/2`, which additionally carries:

| Field | Content |
|---|---|
| `log_evaluations` | `K` from P2, as reported by `mm omega-min` |
| `series_error_bound` | `K · 2^-precision` from P4, in bits |
| `series_error_bound_omega` | the same divided by `lower(M_total)` |
| `epsilon_margin_ratio` | `max_epsilon / series_error_bound` |
| `gap_margin_ratio` | `gap / series_error_bound_omega` |
| `precision_source` | `derived` or `override` |

The record MUST state `log_precision_bits`, `rational_bits`, and `gap` together with the two margin ratios, so that a reader can check P5 from the record alone without rerunning anything. `precision_source` MUST be `override` whenever `--precision` was supplied, and an override MUST NOT be recorded as `derived` even when it happens to equal the derived value; the distinction is whether the number was chosen by the rule.

The replacement is clean. No reader accepts `matrix-math-certification-record/1`, and no record carries both spellings. The certification record is a producer artifact under a run directory; it is not part of any certificate, is not hashed into a canonical digest, and no checker reads it.

### 4.5 The checker is unchanged

The checker MUST continue to validate `log_precision_bits` against `[32,4096]` in the schema decoder before evaluation, with the stable code the `schemas/fixtures/invalid/omega_bad_precision.json` fixture pins (§6.5). It MUST continue to derive every series length from that field through the `0002_spec.md` §3.2 selection function, and MUST NOT treat the field, or any other certificate field, as a term count, loop bound, or array length (§7.3).

A checker MUST NOT acquire a preferred precision, a minimum above 32, or a warning path for a low declared value. A certificate that declares too few bits is rejected by the A21 inequality it fails to satisfy, which is the correct mechanism; adding a second one would put a producer policy inside the trusted surface.

## 5. The operational default

### 5.1 The value

The default `log_precision_bits` is **64**.

It is the least power of two at or above the precision P5 derives at the largest certified instance. §3.1 and §4.2 give that derivation: `K = 83,012`, `ε_emit = 7.4624 × 10^-10`, and

```text
p ≥ log2(1000 × 83,012 / 7.4624 × 10^-10) = 56.63,
```

so P5 selects 57, and 64 is the next power of two. The default therefore carries `2^7 = 128` times the margin P5 already requires, on top of P5's own factor of one thousand. At `ℓ*=2` P5 selects 55, so the same default covers that instance with `2^9` to spare.

Powers of two are the grid because the field counts bits and because the next step up, 128, is where the default MUST move if a future instance derives a requirement above 64. `ℓ*=4` has not been certified, so the `K` and `ε` it would produce are not yet measured; §7 records what happens when they are.

The default is a starting point, not a licence to skip P5. A producer MUST apply P5 to every certificate it emits, and MUST use the derived value when it exceeds the default.

### 5.2 What changes

Every location in §1.2 changes from 256 to 64, except that the `PRECISION` parameter of the `justfile` recipe `certify` is deleted rather than re-defaulted: the recipe becomes `certify RUN`, and a run that wants an explicit value passes `--precision` to `python -m mm_opt.certify` directly and is recorded as an override under §4.4. `python/mm_opt/optimize.py` and `python/mm_opt/certify.py` lose their `256` fallbacks in the same change, because §4.3 requires both fields to be set in the configuration.

`crates/mm-exact/tests/omega_fixtures.rs` asserts the declared precision of the hand fixture; that assertion moves to 64 with the fixture.

### 5.3 What is regenerated, and what is not

`just fixtures` regenerates the `python/mm_opt/omega_fixtures.py` outputs at the new default: `tests/vectors/omega-l2-hand.json` and the invalid fixtures `omega_feasibility_violated.json` and `omega_negative.json`. `omega_bad_precision.json` declares 8 in order to be out of range and is unaffected by the default.

Each regenerated fixture's canonical digest changes, and the digest MUST be updated everywhere it appears in the same change. For the hand fixture that means the generated Lean module `lean/MatrixMath/Generated/Omega_fb1db26360134720.lean`, whose filename and theorem names are the digest prefix, and every place that names it. A fixture whose digest is stale somewhere is worse than no fixture, because `just verify` and the release verifier both key on the digest.

The two published Track A certificates — `tests/vectors/omega-l2-optimized.json` and `tests/vectors/omega-l3-optimized.json` — are **not** regenerated. They declare 256, they are accepted at 256, and the bound each carries is correct as it stands. Regenerating them would change the canonical digest, the generated Lean module, and the experiment record, and would cost a 110-minute `native_decide` proof, in exchange for nothing mathematical. §0.5 of `0001_spec.md` removes any obligation to migrate them; it does not create an obligation to churn them. The next certificate produced at each instance will use the derived precision, and the experiment record will say so.

## 6. What must not change

The following are outside the scope of this document and MUST NOT be altered by the change it specifies:

- the `[32,4096]` range of `log_precision_bits` in §6.5, and the decoder's rejection of anything outside it;
- the canonical omega certificate schema, its field set, its ordering, and its digest rules;
- the meaning of `log_precision_bits` as a target accuracy under §7.3 and `0002_spec.md` §3.5;
- the §7.2 propagation rules, the `Ω ≥ 0` validation, and the A21 inequality; and
- the contents of any published certificate.

This is a producer policy change plus a default. If applying it requires editing `crates/mm-schema`, `crates/mm-exact`, or `lean/MatrixMath/Certificate/`, the change has left its scope.

## 7. Milestone

### 7.1 M6-P — derived precision selection

M6-P is a follow-on to M6 (§14.9), which is recorded complete. It is not a new position in the M-1 through M8 sequence and it does not gate M7.

**Inputs:** M6 complete, and `0002_spec.md` M4-R complete.  
**Deliverables:** the `log_evaluations` field on `mm omega-min`; P5 and its iteration in the producer; `matrix-math-certification-record/2`; the new default in every §1.2 location; regenerated fixtures with updated digests; and updated experiment records and implementation status.

Implementation order:

1. count directed logarithm evaluations in `crates/mm-exact` and report the P2 figure as `log_evaluations` from `mm omega-min`;
2. assert the counts of P3 — 83,012 at `ℓ*=3` and 1,028 at `ℓ*=2` — in `crates/mm-exact/tests/omega_fixtures.rs` against the committed vectors;
3. implement P5, its four-iteration bound, and the `rationalization_failed` exhaustion path in `python/mm_opt/certify.py`;
4. replace the certification record schema with version 2 and its six new fields;
5. change the default to 64 in every §1.2 location and delete the `certify` recipe's `PRECISION` parameter;
6. regenerate the `just fixtures` outputs and update every recorded digest, including the generated Lean module name; and
7. update `docs/experiments/omega-l2.md`, `docs/experiments/omega-l3.md`, and `docs/implementation-status.md`.

Acceptance commands:

```bash
just build
just lint
just test
just fixtures
just verify tests/vectors/omega-l2-hand.json
just certify data/optimize/omega-l3-refine-8a71318e3bca8073
```

Acceptance details:

- `mm omega-min` reports `log_evaluations` equal to 83,012 on `tests/vectors/omega-l3-optimized.json` and 1,028 on `tests/vectors/omega-l2-optimized.json`;
- the producer selects 57 at the recorded `ℓ*=3` point and 55 at the recorded `ℓ*=2` point, matching Appendix A;
- a point whose `ε` is small enough to demand more than 64 bits selects more, and one whose four iterations do not converge returns `rationalization_failed`;
- the certification record states `log_precision_bits`, `rational_bits`, `log_evaluations`, both margin ratios, and the gap, and P5 can be rechecked from those fields alone;
- re-certifying the recorded `ℓ*=3` float point at the new default yields a certified `Ω` differing from the certified `Ω` at 256 bits by less than `10^-12`;
- the regenerated fixtures verify, and no stale digest remains in Lean, Rust, Python, or documentation; and
- `tests/vectors/omega-l2-optimized.json` and `tests/vectors/omega-l3-optimized.json` are byte-identical to their committed forms.

The `10^-12` figure is a bound, not a prediction. The predicted difference is smaller: each of `lower(E_total)`, `lower(M_total)`, and `upper(log2(q+2))` moves by at most `K · 2^-64 = 4.5001 × 10^-15`, and propagating those through `Ω = (requirement - E_total) / M_total` gives at most

```text
4.5001 × 10^-15 × (2 + 2.372156220666) / 3.015265574536
  = 6.53 × 10^-15,
```

about 150 times inside the acceptance bound. `10^-12` is the bound to state because it is below the `3.5 × 10⁻¹²` certification gap the producer already records: a precision change that moved `Ω` by more than the gap would be a change worth investigating regardless of what this model predicts. A failure of this criterion is a defect in the change, not a licence to raise the default back.

## 8. Risks and fixed fallbacks

| Risk | Detection point | Required fallback |
|---|---|---|
| `ℓ*=4` derives a precision above 64 | M6-P applied to the first `ℓ*=4` point | raise the default to 128 and re-derive; never carry an instance-specific precision as a global default |
| `ε` is not available before the precision is fixed | producer bootstrap on a new instance shape | select by P6 and record `precision_source` as `derived`; do not fall back to a literal |
| The P5 iteration does not converge in four rounds | `just certify` | return `rationalization_failed`; do not emit at the last precision tried |
| P1's composition constant is wrong at some precision | `crates/mm-rat/tests/numerics.rs` width assertion | widen the assertion's value table and re-derive; do not weaken P4 |
| A published certificate is rejected at a lower default | any `just verify` after M6-P | leave the published bytes alone and investigate the checker; a published artifact is never re-emitted to accommodate a default |
| A regenerated fixture's digest is stale in one place | `just lint`, `just test`, `just verify` | fix every location in one change; never pin a second copy of the old digest |

No fallback may raise the default without the derivation in §5.1 being redone against measured values.

## Appendix A — Derived precision at the recorded instances

A ratio below one means the accumulated series error exceeds the quantity it must not disturb. Both 32-bit rows are below one in both columns, which is §3.2's conclusion stated once more as a table. `lower(M_total)` is `1.497520161605` at `ℓ*=2` and `3.015265574536` at `ℓ*=3`; the recorded certification gaps are `8.5 × 10⁻¹¹` and `3.5 × 10⁻¹²`.

`ℓ*=4` has no row. No `ℓ*=4` point has been certified, so its `K` and `ε` are not yet measured, and §7 fixes what to do when they are.
